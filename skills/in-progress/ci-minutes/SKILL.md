# CI minutes / Минуты Actions

Брифинг для агента в репозитории, который делит один аккаунт GitHub с
другими. Прочитай целиком, **замерь свой репозиторий**, сделай через
`unlazy` (гейты до работы, мутации, перепроверка), отчитайся числами, а не
словом «вдвое». Всё ниже — из настоящей поломки, замеренной 20 сентября в
`DVronard/HL`; числа оттуда даны как ориентир, у тебя они свои.

## 1. Что случилось и как это выглядит

На Free у **приватных** репозиториев 2000 минут Actions в месяц **на весь
аккаунт**, лимит трат по умолчанию $0. Когда они кончаются, GitHub просто не
выдаёт раннер. Признаки, по которым это отличается от падения кода:

```
джоб «failure» за 1–3 секунды          started_at ≈ completed_at
логов нет                               скачивание логов → HTTP 404
раннер не назначен                      runner_id: 0, runner_name: ""
шагов нет                               в объекте джоба нет steps
workflow-файл не менялся                git log -- .github/workflows/
```

Не верь полю `billable` из API прогона — оно теперь 0 и у настоящих зелёных
прогонов. Не «перезапускай» джоб: раннера от этого не появится. Не
отключай, не пропускай и не карантинь тесты, чтобы «позеленело».

Где смотреть у владельца: **Settings → Billing and plans → Usage this
month → Actions**; там же дата сброса.

## 2. Сначала замер: сколько стоит один прогон

Возьми последний **зелёный** прогон и его джобы через API (MCP
`actions_list` → `list_workflow_jobs`, или `gh api
repos/OWNER/REPO/actions/runs/RUN_ID/jobs`). У каждого джоба есть
`started_at`/`completed_at`. **GitHub округляет каждый джоб до минуты
вверх**, и складывать надо округлённые:

```
HL, прогон #116:
  бэкенд : 264 с — ffmpeg 26 с, зависимости 22 с, дубль-шаг 48 с, тесты 156 с → 5 мин
  фронт  :  64 с                                                            → 2 мин
  итого 7 минут за прогон; 122 прогона с 12 сентября ≈ 854 минуты
```

Посчитай, сколько прогонов было за месяц (`list_workflow_runs`, все
страницы) и умножь. Это число идёт в changelog как «было».

## 3. Три правки, у каждой названа цена

### 3.1. Один workflow на сторону, у каждого свой `paths`

Вместо одного `ci.yml` с двумя джобами — `backend.yml` и `frontend.yml` (или
как у тебя называются стороны), у каждого свой список `paths`, **включающий
сам файл workflow** — иначе правка фильтра не проверяется.

```yaml
on:
  pull_request:
    paths:
      - "web/**"
      - ".github/workflows/frontend.yml"
```

**Оговорка, без которой правка бесполезна.** Фильтр `paths` на
`pull_request` смотрит на **все файлы PR относительно базы**, а не на
последний пуш. PR, где есть и бэкенд, и фронт, платит за обе стороны на
каждом пуше — фильтр не экономит ничего. Поэтому правило (в `CLAUDE.md`
репозитория): **одна сторона — один PR**; docs можно класть в любой, они не
запускают ничего. Пушить — по готовности партии, не по коммиту: каждый пуш
это прогон.

Что фильтр не ловит: файлы вне тестируемого кода, но внутри папки
(`backend/Dockerfile`) всё равно гоняют тесты; папки, которые CI не гоняет
(`bench/`), в `paths` не входят вовсе. Назови это в changelog.

### 3.2. Убрать дубли шагов; сторож пропусков — точный

Найди шаги, которые гоняют одни и те же тесты дважды (в HL: отдельный шаг
«ffmpeg-тесты не пропущены» на четыре файла, потом `tests/` целиком — те же
четыре файла ещё раз, 48 секунд и лишняя минута в счёте). Оставь один
прогон, а сторож пропусков сделай **точным**: он смотрит пропуски именно
тех файлов, ради которых ставится зависимость. Слепой `! grep -q skipped`
на полном наборе падает на первом же законном пропуске.

Шаг из `backend.yml` HL, дословно (адаптируй имена файлов и команду):

```yaml
      - name: Тесты — один прогон, ffmpeg-тесты под сторожем
        shell: bash
        run: |
          cd backend
          python -m pytest -q tests/ -rs | tee /tmp/tests.txt
          grep -qE "[0-9]+ passed" /tmp/tests.txt
          ! grep -qE "^SKIPPED .*(test_audio_tracks_ffmpeg|test_render_one_pass|test_audio_levels_ffmpeg|test_atime)\.py" /tmp/tests.txt
```

**`shell: bash` обязателен.** Без него GitHub запускает `bash -e` **без
pipefail**, и упавший pytest за `| tee` считается прошедшим — `grep`
находит «passed» и в строке «3 failed, 1000 passed». Прибор в HL держит
контроль: под `bash -e` та же команда с упавшим pytest даёт код 0. Проверь у
себя так же, а не поверь на слово.

### 3.3. Убрать прогон на `push: main`

PR проверяется на merge-ref (слияние головы с базой). После сквош-мержа
дерево на `main` совпадает с проверенным — сверяй хешем
(`git rev-parse HEAD^{tree}` до и после `git merge origin/main`). Повторный
прогон на `main` стоил 7 минут на каждый мерж и не добавлял ничего.

**Цена:** если база сдвинулась между последней проверкой PR и мержем,
`main` не проверен. У одного разработчика с одной веткой это не случалось;
вернуть — одна строка. Если в репозитории мержат несколько человек
параллельно — оставь `push: main`, но с теми же `paths`.

## 4. Проверка до пуша (гейты леджера)

1. **Фильтр путей** — прибор на picomatch (`{dot: true}`) с наборами файлов
   PR: только docs → ничего; только бэкенд → бэкенд; только фронт → фронт;
   правка workflow → свой; lock-файл и конфиги **вне `src/`** → своя
   сторона (мутация `web/**` → `web/src/**` в HL прошла мимо прибора, пока
   этого случая не было). Положительный контроль: `backend/*` не должен
   ловить вложенный файл. Помни: это твоя реализация семантики, не сама
   GitHub — так и напиши.
2. **Сторож** — извлеки блок `run:` из YAML и прогони под `bash -eo
   pipefail` с подставным `python` на PATH: законный пропуск проходит;
   пропуск каждого из охраняемых файлов падает; pytest с кодом 1 и словом
   «passed» падает; без `shell: bash` — проходит (это контроль).
3. **Шаги те же** — сравни разобранный YAML со старым `ci.yml`: шаги других
   джобов байт-в-байт; `push` отсутствует; `paths` включает сам файл.
4. **Дословный прогон** — команды шага локально, не пересказ.
5. **actionlint** — `pip install actionlint-py`, ноль замечаний.
6. **Мутации** — минимум: убрать self-path; `**` → `*`; убрать сторож;
   снять `shell: bash`; вернуть `push: main`. Каждая должна уронить свой
   гейт.
7. **Замер «стало бы»** — по своим прогонам за день с той же моделью цены.
   HL: было 126 минут → 52 (−58 %).

## 5. Если минут всё равно не хватает

Свой раннер на машине владельца (`runs-on: self-hosted`; минуты не
тратятся, код не открывается; нужны python/node/ffmpeg на машине) или
публичный репозиторий (минуты безлимитны, код открыт). Решает владелец.

## 6. Что записать

В changelog: признаки отказа, замер «было», три правки с ценой, оговорку
про семантику `paths`, дыру pipefail, число «стало бы». В `CLAUDE.md`:
правило «одна сторона — один PR» и «пушить по готовности партии».
